이 블로그 글이 지켜야 할 기준. 글 쓸 때마다 참고하고, 새로 걸린 AI티가 있으면 여기 추가한다.

> **작업 순서**: ① Claude로 초안 → ② humanize-korean 스킬 돌리기(문법·수사 패턴 자동 제거) → ③ **아래 "사람이 잡아야 하는 것"을 눈으로 점검** → ④ 로컬 미리보기 → ⑤ 발행. humanize가 ②에서 많이 잡지만 ③은 못 잡는다. 그게 이 문서의 핵심.

---

## 0. 기본 목소리

- **평서체(~다/~했다).** 격식체(~습니다)나 해요체로 흐르지 않는다.
- **담백하게.** 과장·감탄·오글거리는 마무리 금지.
- **짧게, 그리고 리듬을 흔든다.** (아래 3번 참고 — 이게 제일 중요)
- 결과·수치·의사결정 중심. 코드 덤프 아님(로직·다이어그램까지만).

---

## 1. ★ 사람이 잡아야 하는 것 (humanize가 못 잡음)

humanize 스킬은 번역투·기계적 병렬·접속사 남발 같은 **문법/수사 패턴**은 잡는다. 하지만 아래는 사람 눈으로만 잡힌다. **발행 전 반드시 직접 점검.**

### 1-1. 어색한 비유·표현 선택
사람이 실제로 잘 안 쓰는 표현. "틀린 문법"이 아니라 "안 쓰는 말"이라 자동 탐지가 안 된다.
- ❌ "약한 모델을 **맨몸으로 붙였다**" → ✅ "약한 모델한테 **그냥 시켰다**"
- ❌ "이게 **사활이 걸린** 부분이다" → ✅ "이게 제일 중요하다"
- 리트머스: **"내가 친구한테 말할 때 이렇게 말하나?"** 아니면 바꾼다.

### 1-2. 과장된 극적 프레이밍
- ❌ 소제목 "**반전!** — ...", "**충격적이게도**", "**놀랍게도**"
- ✅ 덤덤하게. "그런데 알고 보니...", "근데 원래 자동이라는데?"
- 삽질기·회고는 **덤덤할수록** 진짜 같다.

### 1-3. 사실 정확성 (발행 전 팩트체크)
- 단정하기 전에 **공식 문서로 확인.** (예: "Share to profile 무조건 필수" → 확인해보니 "원래 자동, 지연 시 수동"이었음)
- 모르면 "~인 듯하다", "~인 것 같다"로 정직하게. 아는 척 단정 금지.

### 1-4. 진짜 캡처만
- 이미지는 **실제 스크린샷만.** 실제처럼 보이는 일러스트를 캡처인 척 넣지 않는다. (정직성이 이 블로그의 무기)
- 재현물이면 "재현 이미지"라고 명시하거나 뺀다.

## 2. 금지 표현 사전 (걸리면 교체)

### 2-1. AI 버즈워드 (영어권 tell을 한국어로 옮긴 것 포함)
- 하다: 활용하다(→쓰다), 극대화하다, 최적화하다(맥락 없이), 혁신적인, 원활한, 강력한(robust 번역), 견고한
- 명사: 여정(journey), 풍경/지형(landscape), 영역(realm 남발), 태피스트리, 게임체인저, 솔루션(막연할 때)
- 동사: 파헤치다(delve), 탐험하다(맥락 없이), 항해하다(navigate 비유), 촉발하다

### 2-2. 기계적 표현
- "~뿐만 아니라 ~도" (기계적 병렬)
- "~라는 점에서 의미가 있다", "~라고 할 수 있다" (공허한 마무리)
- "결론적으로", "요약하자면", "정리하면" (당연한 접속 남발 — 없어도 되면 뺀다)
- 문두 접속사 남발: "그래서/그러나/또한/게다가"로 매 문단 시작하지 않기 (5회 넘으면 줄인다)

### 2-3. 문장부호
- **em대시(—) 남용** 금지. 한 글에 한두 번이면 몰라도 극적 효과용 반복은 AI티.
- 느낌표 남발, 말줄임표(...) 남발 금지.
- 이모지·불릿 과다 금지. (불릿은 진짜 목록일 때만)

## 3. ★ 구조·리듬 (AI 탐지의 1순위 신호)

문장 길이·어미가 균일하면 어휘가 아무리 자연스러워도 기계처럼 읽힌다. **구조가 어휘보다 중요하다.**

### 3-1. 어미를 흔든다
모든 문장이 "~다"로 끝나면 AI티. 섞어라:
- 질문: "그럼 내 경우는?", "안 뜨면?"
- -더라: "정상값이더라", "있더라"
- 연결어미로 끊기: "멀쩡했고.", "헛발질이었고."
- 짧은 조각: "딱 절반 남짓.", "그런데 안 떴다."
- 후회/구어: "캡처나 해둘걸."

### 3-2. 문장 길이를 섞는다
- 짧은 문장(3~8자)과 긴 문장(20자+)을 섞는다.
- 균일한 15~25자 문장 연속 = 로봇. 짧게 치고, 길게 풀고, 다시 짧게.

### 3-3. "3의 규칙" 남발 주의
- AI는 뭐든 3개씩 나열한다("A하고, B하고, C한다"). 가끔은 2개, 가끔은 4개, 가끔은 그냥 1개로.

## 3.5. ★ 본받을 좋은 패턴 (잘 쓰는 개발 블로그에서)

"하지 말 것"만큼 "이렇게 하면 좋다"도 중요하다. 인기 트러블슈팅/회고 글(N+1 여행기, f-lab 면접관 관점 등)에서 뽑은 패턴. **주의: 그들의 슬랭·구어체 톤은 따라하지 말 것. 가져올 건 톤이 아니라 (1) 구성 뼈대 (2) 시행착오를 숨기지 않는 솔직함이다.** 솔직함과 담백함은 양립한다 — "처음엔 캐시 문제라고 봤다. 틀렸다."처럼.

### 글 열기
- **현장 문제 장면으로 연다** (개념 정의로 시작 금지). "게시글 목록 한 번 부르는데 쿼리가 22번 나갔다."처럼 구체적 상황부터 → 정의·배경은 그 뒤.
- **"왜 이 글을 쓰는가" 맥락을 한두 줄 먼저** 깐다. (기획 맥락에서 출발한 문제해결 = 포지셔닝과 일치)
- **결론(핵심)을 서두에 한 번 박고, 끝에 다시** (두괄식). 채용담당자는 스캔한다 — 끝까지 안 읽어도 역량이 전달되게.

### 본문 (트러블슈팅의 핵심)
- **"추정 → 소거 → 검증" 논리 사슬**로 쓴다. 특히 **틀린 가설을 소거해간 과정**을 남긴다. 이게 문제해결 역량의 직접 증명 = 채용에서 제일 강력.
- **실패한 시도를 지우지 말고** "시도 1(실패)→시도 2(새 문제)→원인→시도 3(최종)"으로 남긴다. 실패 경로가 사고 과정의 증거.
- **검증 가능한 근거**: "빨라졌다" ❌ → "22개 → 3개 쿼리" ⭕. 실측·비교표·전후 수치를 붙인다. (이 블로그의 무기)
- **코드·에러·로그를 세 층위로 섞는다**: ① 코드 블록 ② 실제 에러/로그 원문(복붙 가능하게, 검색 유입+신뢰) ③ 사람 말 해설. 셋을 번갈아.

### 독자 배려 · 마무리
- **가장 모르는 사람 기준**으로 전제를 깔되, 곁가지 용어는 **외부 링크로 위임**(다 설명하면 본론이 묻힌다).
- **마무리 = 결과 요약 + 배운 점 + (있으면) 다음**. 감상 나열로 끝내지 말 것. "교훈" 섹션이 성찰력의 증거.
- **본인 인사이트 1스푼 필수**. 복붙·코드 나열·두서없는 정리는 면접관이 바로 거른다. 도입 이유·과정의 문제점·결과 평가 중 하나는 반드시 내 관점으로.
- **"오늘 ~를 배웠다"식 일기 나열 금지**. "특정 상황에서 내가 한 경험"으로 소재를 잡는다.

> 한 줄 요약: **현장 문제 장면으로 열고 → 추정·소거·검증 사슬로 풀되 실패도 남기고 → 전후 수치로 증명하고 → 배운 점으로 닫는다.** (참고: f-lab.ai/en/blog/developer-blog-tips = 면접관 관점, 최우선)

## 4. 글 유형별 뼈대 (스펙 §3)

1. **프로젝트 회고**(projects): 한 줄 요약 → 문제 정의 → 접근·의사결정(왜) → 만든 것(로직·다이어그램) → 결과(공개 가능 수치) → 회고
2. **트렌드 조사·평가**(trends): TL;DR 3줄 → 정의·맥락 → 왜 지금 뜨나 → 직접 본 장단점/내 평가 → 언제 쓰고 피할지 → 출처
3. **써봤다 후기**(trends, series): 한 줄 평 → 뭐길래 써봤나 → 셋업·첫인상 → 실제로 시켜본 것(결과·스크린샷) → 좋았던/막힌 점 → 결론
4. **TIL**(notes): 오늘 배운 것 1개 → 코드/예시 → 헷갈린 점 → 한 줄 정리
5. **툴/워크플로우**(tools): 문제 → 내 워크플로우 → 설정/코드 → 효과 → 재현 방법
